\label{sec:framework}

Approximate accelerator design must identify arithmetic-unit configurations that improve hardware efficiency while preserving application accuracy. The configuration space grows combinatorially, yet evaluating each design through logic synthesis and application execution is costly. ApproxPilot-SE addresses this challenge by starting with a small set of measured designs and using measurements collected during exploration to calibrate latency predictions and refine the surrogate models that guide subsequent search. We first formulate arithmetic-unit selection as a multiobjective optimization problem, then describe how ApproxPilot-SE solves it under a limited evaluation budget.


\subsection{Problem Formulation}
\label{subsec:problem_formulation}


Given a target RTL design and an approximate arithmetic-unit library, the optimization task is to select a suitable implementation for each configurable arithmetic site. Different combinations of arithmetic units produce different trade-offs between PPA and application accuracy.


Before constructing the design space, we prune the arithmetic-unit library using the strategies adopted in ApproxPilot~\cite{zhang2025approxpilot}. Each unit is characterized by its arithmetic error, area, power, and latency. Dominated units are removed through multiobjective comparison. The remaining units form the candidate library for design optimization.

Let $N$ be the number of configurable arithmetic sites. For site $i$, let $e_i$ denote its exact implementation and $\mathcal{A}_i$ the set of compatible approximate implementations after pruning. The legal implementation set and the complete design space are defined as
\begin{equation}
    \mathcal{C}_i = \{e_i\} \cup \mathcal{A}_i,
    \qquad
    \Omega = \prod_{i=1}^{N}\mathcal{C}_i.
    \label{eq:se_configuration_space}
\end{equation}
A candidate design is represented by $\mathbf{x}=(x_1,\ldots,x_N)\in\Omega$, where $x_i$ specifies the implementation selected for site $i$.

Each configuration has its own area $A(\mathbf{x})$, power $P(\mathbf{x})$, latency $L(\mathbf{x})$, and application accuracy $Acc(\mathbf{x})$. Let $A_{\mathrm{ex}}$, $P_{\mathrm{ex}}$, and $L_{\mathrm{ex}}$ denote the PPA metrics of the fully exact design. We formulate the optimization problem as
\begin{equation}
    \min_{\mathbf{x}\in\Omega}
    \mathbf{f}(\mathbf{x}) =
    \left(
        \frac{A(\mathbf{x})}{A_{\mathrm{ex}}},
        \frac{P(\mathbf{x})}{P_{\mathrm{ex}}},
        \frac{L(\mathbf{x})}{L_{\mathrm{ex}}},
        1-\mathrm{Acc}(\mathbf{x})
    \right).
    \label{eq:se_search_objectives}
\end{equation}

Here, larger values of $Acc(\mathbf{x})$ indicate higher accuracy. The first three objectives minimize normalized PPA, while the fourth maximizes accuracy. The goal is to find competitive configurations with different PPA and accuracy trade-offs.
















\subsection{Framework Overview}
\label{subsec:framework_overview}

Fig.~\ref{fig:framework} organizes ApproxPilot-SE into initialization, surrogate-guided candidate search, evaluation and model updating, and final configuration selection. After training initial GNN surrogates on measured designs, the framework repeatedly searches for promising candidates, evaluates a selected batch, and uses the new measurements to update both the models and the calibration references. The updated predictions then guide further search. This interaction makes the DSE self-evolving: search determines which new data are collected, and those data improve the predictions used to identify the next candidates. The process continues within the evaluation budget and outputs feasible designs according to the user-specified constraints. Section~\ref{sec:surrogate_models} describes the model architectures, training, and latency calibration.

\noindent\textit{1) Initialization:}
ApproxPilot-SE samples an initial set of legal arithmetic-unit configurations from $\Omega$ and evaluates them through logic synthesis and application execution. The measured PPA and application accuracy form the initial labeled dataset $\mathcal{D}_0$. Two GNN-based surrogate models are constructed and trained on these data, one for PPA and the other for application accuracy. The measured configurations also initialize the latency calibration reference set $\mathcal{R}_0$. Initialization thus provides both the prediction models and measured references required to begin exploration.

\noindent\textit{2) Surrogate-Guided Candidate Search:}
NSGA-III~\cite{deb2014nsgaiii} generates candidate configurations whose PPA and application accuracy are estimated by the current surrogates. Latency predictions are corrected using the current calibration references when a suitable reference is available. The predicted objectives support Pareto ranking and selection, allowing the search to identify promising trade-offs without synthesizing and executing every candidate. While the next evaluation batch is being collected, the models and references remain fixed. NSGA-III continues exploring and refining the candidate set until enough previously unevaluated, Pareto-relevant configurations have been selected to fill the round's batch budget. A portion of the batch is reserved for candidates just below the predicted accuracy threshold to reduce the risk of overlooking feasible designs because of prediction errors.

Let $\mathcal{U}_t$ denote the set of unique, previously unevaluated configurations available for selection at round $t$. The predicted accuracy retention is defined as
\begin{equation}
    \widehat r_t(\mathbf{x})
    =
    \frac{\widehat{\mathrm{Acc}}_t(\mathbf{x})}
    {\mathrm{Acc}_{\mathrm{ex}}},
    \label{eq:se_predicted_retention}
\end{equation}
where $\mathrm{Acc}_{\mathrm{ex}}$ denotes the measured accuracy of the fully exact configuration. Given an acquisition threshold $\tau_{\mathrm{acq}}$, the candidates are partitioned into
\begin{equation}
\begin{aligned}
    \mathcal{U}_t^{+}
    &=
    \left\{
    \mathbf{x}\in\mathcal{U}_t
    \mid \widehat r_t(\mathbf{x})
    \ge\tau_{\mathrm{acq}}
    \right\},\\
    \mathcal{U}_t^{-}
    &=
    \left\{
    \mathbf{x}\in\mathcal{U}_t
    \mid \widehat r_t(\mathbf{x})
    <\tau_{\mathrm{acq}}
    \right\}.
\end{aligned}
\label{eq:se_feedback_partition}
\end{equation}

Candidates in $\mathcal{U}_t^{+}$ are prioritized by nondominated sorting of the predicted PPA and accuracy objectives, with crowding distance used to preserve diversity within a partially selected front. For $\mathcal{U}_t^{-}$, configurations closer to the predicted accuracy boundary receive higher priority. This allows the framework to evaluate both Pareto-relevant designs and candidates whose feasibility may be affected by prediction errors.



\noindent\textit{3) Candidate Evaluation and Model Updates:}
Once the selected batch $\mathcal{S}_t$ has been collected from $\mathcal{U}_t^{+}$ and $\mathcal{U}_t^{-}$, its configurations undergo logic synthesis and application execution. Their measured PPA and accuracy are added to the cumulative training dataset:
\begin{equation}
    \mathcal{D}_{t+1}
    =
    \mathcal{D}_t\cup\mathcal{Y}_t,
    \label{eq:se_dataset_update}
\end{equation}
where $\mathcal{Y}_t$ contains the newly evaluated configurations and their measured labels. Both surrogate models are further trained on the expanded dataset, using the new examples together with previous measurements to refine their predictions. Meanwhile, the newly measured configurations enrich the latency calibration reference set:
\begin{equation}
    \mathcal{R}_{t+1}
    =
    \mathcal{R}_t\cup\mathcal{S}_t.
    \label{eq:se_reference_update}
\end{equation}
The reference residuals are recomputed with the updated latency surrogate, and the framework returns to candidate search in step 2. DSE therefore supplies training examples from regions relevant to optimization, while the refined models and expanded references support more reliable candidate ranking in the next round. This repeated exchange couples surrogate improvement with the discovery of promising configurations rather than treating model training and search as isolated stages.


\noindent\textit{4) Budget Termination and Configuration Output:}
The evaluation budget determines when the search--evaluation--update loop terminates. After feedback acquisition ends, the final models and references remain fixed during the final candidate search. Shortlisted designs are verified using the budget reserved for final evaluation, without further model updates. Once these evaluations are complete, the framework filters the measured designs according to the user-specified constraints and identifies their nondominated configurations. It then returns the preferred feasible configuration or a set of Pareto alternatives according to the user's hardware objectives.
